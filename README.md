# API-testing-framework
# JS AppSec Recon → API Security Testing

> An AI-assisted security testing workflow that transforms JavaScript reconnaissance results into structured API security testing targets.

## Overview

This project provides a two-stage application security workflow:

1. **`js-appsec-recon.skill`** — analyzes JavaScript assets and extracts security-relevant information such as API endpoints, routes, parameters, authentication-related functionality, and other potential attack surfaces.
2. **`api-security-testing-final-clean.skill`** — consumes the reconnaissance results and uses them as input for structured API security testing.

The goal is to create a clear pipeline:

```text
JavaScript Recon
      ↓
API Attack Surface Discovery
      ↓
API Security Testing
      ↓
Manual Validation
      ↓
Reporting
```

## Skills

### `js-appsec-recon.skill`

The first stage of the workflow.

Its purpose is to analyze JavaScript-related attack surface and identify information that can be useful during application and API security testing.

Typical output may include:

* API endpoints
* API routes
* HTTP methods
* Parameters
* Interesting URLs
* Authentication-related endpoints
* Authorization-related functionality
* Client-side functionality
* Potentially sensitive references
* Security-relevant JavaScript patterns
* Additional attack-surface information

The output of this skill is then used as input for the API security testing stage.

---

### `api-security-testing-final-clean.skill`

The second stage of the workflow.

It receives the reconnaissance results generated by `js-appsec-recon.skill` and turns the discovered API attack surface into structured security testing targets.

Depending on the available information, testing may include:

* Authentication
* Authorization
* BOLA / IDOR
* Access control
* Parameter manipulation
* Input validation
* CORS
* Rate limiting
* API endpoint behavior
* HTTP method handling
* Security controls
* Other API-specific security issues

Potential findings should always be manually validated before being considered confirmed vulnerabilities.

---

## Authentication Requirement

`api-security-testing-final-clean.skill` requires **two authenticated sessions from two different accounts** for authorization-related testing.

Provide:

```text
Account 1
└── Cookie 1

Account 2
└── Cookie 2
```

The two cookies must belong to **different accounts**.

Example:

```text
Cookie 1 → Account A
Cookie 2 → Account B
```

The two authenticated sessions are used to compare access between the accounts and help identify authorization issues such as:

* BOLA
* IDOR
* Horizontal Privilege Escalation
* Broken Access Control

> **Important:** Use test accounts that you own or are explicitly authorized to use. Never share or test with session cookies belonging to other users.

## Usage

The two skills are designed to be used sequentially:

```text
js-appsec-recon.skill
       ↓
Reconnaissance Results
       ↓
api-security-testing-final-clean.skill
       ↓
API Security Testing
```

### Step 1 — Run `js-appsec-recon.skill`

Load or invoke:

```text
js-appsec-recon.skill
```

Provide the skill with the JavaScript/application reconnaissance data for an **authorized target**.

The skill analyzes the available JavaScript attack surface and produces security-relevant reconnaissance results.

Typical results may contain:

```text
JavaScript Assets
API Endpoints
API Routes
HTTP Methods
Parameters
Interesting URLs
Authentication-related endpoints
Authorization-related functionality
Potential attack surfaces
Other security-relevant findings
```

---

### Step 2 — Review the Recon Results

Review the output produced by the reconnaissance skill.

For example:

```text
GET  /api/v1/users
GET  /api/v1/users/{id}
GET  /api/v1/profile
GET  /api/v1/orders/{id}
POST /api/v1/auth/login
```

Make sure the discovered information is relevant to the target before passing it to the next skill.

---

### Step 3 — Prepare the Two Accounts

Before running the API security testing skill, prepare two authorized test accounts:

```text
Account A → Cookie A
Account B → Cookie B
```

The accounts should be different so that authorization and cross-account access can be tested.

---

### Step 4 — Pass the Recon Results to `api-security-testing-final-clean.skill`

Take the output generated by:

```text
js-appsec-recon.skill
```

and provide it as the input/context for:

```text
api-security-testing-final-clean.skill
```

Along with the reconnaissance results, provide the two authenticated cookies:

```text
Recon Results
     +
Cookie A → Account A
Cookie B → Account B
     ↓
api-security-testing-final-clean.skill
```

The second skill uses the discovered API attack surface and the two authenticated sessions to perform structured API security testing.

---

### Step 5 — Run API Security Testing

The second skill uses the reconnaissance results to identify and prioritize API security testing opportunities.

For example:

```text
Recon Result:

GET /api/v1/users/{id}
GET /api/v1/orders/{id}
GET /api/v1/profile
```

The API security testing workflow can then focus on areas such as:

```text
Authentication
Authorization
BOLA / IDOR
Access Control
Parameter Manipulation
Input Validation
CORS
Rate Limiting
HTTP Method Handling
```

---

### Step 6 — Validate Potential Findings

Do not automatically consider every result a vulnerability.

Potential findings should be manually validated against the authorized target.

A useful workflow is:

```text
Potential Finding
       ↓
Reproduce
       ↓
Verify Impact
       ↓
Confirm Vulnerability
       ↓
Document Evidence
```

---

### Step 7 — Report Confirmed Vulnerabilities

For confirmed findings, document:

* Affected endpoint
* HTTP method
* Parameters
* Preconditions
* Reproduction steps
* Expected behavior
* Actual behavior
* Security impact
* Evidence
* Suggested remediation

## Methodology

The project follows a simple application-security workflow:

```text
Reconnaissance
      ↓
Asset Discovery
      ↓
JavaScript Analysis
      ↓
Endpoint Extraction
      ↓
API Attack Surface Mapping
      ↓
Authentication Analysis
      ↓
Authorization Testing
      ↓
Parameter & Input Testing
      ↓
Security Control Testing
      ↓
Manual Validation
      ↓
Reporting
```

The two skills are designed to keep reconnaissance and API security testing as separate stages while allowing the output of one stage to feed directly into the next.

## Limitations

This project is intended to assist security testing, not replace manual analysis.

Important limitations include:

* Automated analysis may produce false positives.
* Not every discovered endpoint is necessarily vulnerable.
* JavaScript analysis may not reveal server-side-only functionality.
* Authentication and authorization vulnerabilities often require multiple controlled accounts.
* API behavior may change depending on session state, headers, tokens, roles, or application state.
* Potential vulnerabilities must be manually validated before reporting them.

## Security and Responsible Use

This project is intended for:

* Authorized penetration testing
* Bug bounty programs within their defined scope
* Security research on systems you are authorized to test
* Educational and laboratory environments

**Do not use this project to test systems without authorization.**

Always:

* Respect the target's scope.
* Follow the rules of the applicable bug bounty program.
* Respect rate limits.
* Avoid unnecessary traffic.
* Do not access data belonging to other users.
* Do not modify or delete data unless explicitly authorized.
* Use only accounts and sessions you are authorized to use.
* Manually validate findings before reporting them.
